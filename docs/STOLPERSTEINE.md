# Stolpersteine: was beim Einrichten schiefgehen kann

Für Agenten. Das ist schon einmal passiert. Lies es in Phase 0, damit es bei diesem Besitzer nicht wieder passiert.

| Was passiert ist | Warum | Was der Starter dagegen tut | Was du tust |
|---|---|---|---|
| Zwei Zentralen auf einem Rechner, Einträge landeten mal hier, mal dort | Der Agent hatte vorher eine eigene gebaut, später kam der Starter dazu | `start.py` warnt, wenn schon eine andere läuft; `zentrale_client.py` warnt mit ACHTUNG; `einrichten.py suchen` findet alte | Nie eine zweite neben der ersten benutzen. `docs/EINRICHTEN.md`: alte anhalten, liegen lassen, Einträge nur einzeln nach Ja übernehmen |
| Der Agent hat Seiten der Zentrale „nachgebaut“, sie sahen anders aus als gedacht | Er kannte das Vorbild nicht und hat selbst entworfen | Bilder in `docs/REFERENZ.md` | Den Code der Zentrale nicht umbauen. Sieht etwas anders aus als auf den Bildern: Fassung prüfen, Update holen. Wünsche an die Zentrale als Wunsch notieren und dem Besitzer sagen |
| Nach dem Update sah alles aus wie vorher | `git pull` gemacht, aber die laufende Zentrale nicht neu gestartet | Fassung unten links, ACHTUNG im Client, oranger Hinweis auf der Seite | `py einrichten.py update` (sichert Eigenes, holt, verteilt Regeln, startet neu, prüft die Einträge) |
| Berichte zeigten alle Fragen am Stück, der Besitzer wusste nicht, was er antworten soll | Fragen standen im Text oder alle in einem `--frage` | Die Zentrale teilt mehrere Fragen in einem `--frage` selbst auf; Seite zeigt sie nacheinander | Format aus `AGENTS.md`, „So sieht ein Bericht aus“: je Entscheidung ein `--frage` mit Vorschlägen |
| Beim Update drohten eigene Änderungen am Code verloren zu gehen | Der Agent hatte Seiten selbst umgebaut, das Update überschreibt sie | `update` legt alles Eigene vorher in einen Sicherungszweig und zählt die Einträge | Code der Zentrale nicht selbst ändern; Wünsche als Wunsch. Nach dem Update die Sicherung mit dem Besitzer durchgehen |
| Regeln galten nur in diesem Ordner, in anderen Projekten arbeitete der Agent anders | `REGELN.md` stand nur hier | `regeln_verteilen.py`, ACHTUNG im Client, wenn sie fehlen | Nach jedem Update `py regeln_verteilen.py` (macht `update` von selbst) |
| Eigene Regeln waren nach dem Update weg und lagen nur noch im Sicherungszweig | `REGELN.md` ist die Vorlage und kommt mit jedem Update neu | Eigene Regeln stehen in `REGELN.lokal.md`, das Skript `regeln_verteilen.py` übernimmt alte Änderungen von selbst | Nichts in `REGELN.md` ändern, nur in `REGELN.lokal.md` |
| Ein Agent in T3 Code kannte die Regeln nicht | Er läuft mit eigenem `CODEX_HOME` oder `CLAUDE_CONFIG_DIR` | `py regeln_verteilen.py --ziel <datei>` merkt sich die Anleitung für alle weiteren Updates | Einmal einrichten, danach läuft es von selbst |
| Platte voll mit `.venv`, `node_modules`, Caches, uv-Versionen | Jedes Projekt legt eigene Umgebungen an, nichts räumt auf | `aufraeumen\putzen.py` und die tägliche Putzrunde (`docs/PUTZEN.md`) | Erst `--probe`, dem Besitzer zeigen, nach Ja `--los` |
| Lange Texte kamen unter PowerShell kaputt an | Anführungszeichen und Umlaute in Befehlen | `--text-datei` bei Berichten, Notizen, Wünschen | Längeres immer erst in eine Datei (UTF-8), dann `--text-datei` |
| Autostart startete nicht | Python aus dem Microsoft Store (Platzhalter unter `WindowsApps`) | Hinweis in `docs/AUTOSTART.md` | Python von python.org nehmen |
| Konsolenfenster blitzten jede Minute auf | Hintergrund-Skripte mit `py` statt `pyw` | Melder und Putzrunde laufen unter `pyw` ohne Fenster | In der Aufgabenplanung immer `pyw.exe` |
| Ein anderes Gerät erreichte die Zentrale nicht (403 oder Meldung „nur Tailscale“) | Sie hört standardmäßig nur auf den eigenen Rechner, und seit Fassung 2026-11-05 nimmt sie das normale Heimnetz nicht mehr an, weil Schlüssel dort mitlesbar wären | `start.py --heimnetz`, Hinweis „Abgewiesen“ auf der Seite Geräte und im Befehl `geraete` | Tailscale einrichten, Melder mit der Tailscale-Adresse neu einrichten (`docs/HOMELAB.md`, Schritt 2 bis 4), nach Ja. `--lan-unverschluesselt` nur für Geräte, auf denen Tailscale nicht läuft |
| Agent wollte Passwörter oder Schlüssel in den Chat holen | Bequemer Weg | Schlüssel liegen in Dateien, der Besitzer-Schlüssel wird nur einmal angezeigt | Nie Schlüssel oder Passwörter lesen, schreiben oder wiederholen |
| Sicherung meldete „fertig“, aber Dateien fehlten (zwei Ordner gleichen Namens, eigener Ordner `bin`, nicht lesbarer Ordner) | Gleiche Namen überschrieben sich, mehrdeutige Namen galten als Müll, Lesefehler zählten nicht | `sichern.py` bricht bei gleichen Namen vorher ab, sichert `bin`/`build` außerhalb von Projekten, endet bei jedem Fehler mit UNVOLLSTÄNDIG und legt `_sicherung.json` ans Ziel | Endet es mit UNVOLLSTÄNDIG: nichts darauf aufbauen, dem Besitzer sagen, was fehlt |
| Ein verschobener Ordner ließ sich nicht zurückholen | Das Protokoll hatte eine halbe letzte Zeile, das fiel erst nach dem Verschieben auf | Alle Werkzeuge prüfen das Protokoll vor jeder Änderung und brechen bei einer kaputten Zeile ab | Meldung zeigt die Zeile: Kopie der Datei machen, Zeile reparieren, dann weiter |
| Auf eine Frage kam keine Antwort, der Agent wartete endlos | Der Besitzer war nicht da | `berichte-warten` endet nach der Wartezeit | Mit dem Rest weitermachen, Stand als Notiz am Wunsch |
| Messen einer Festplatte hing über eine Stunde | `os.walk` folgt Windows-Verbindungen (Junctions) in jeder Python-Fassung, auch in Schleifen | `inventur.py`, `putzen.py`, Protokoll und Papierkorb gehen seit Fassung 2026-11-07 nicht mehr hinein | In eigenen Skripten Unterordner mit `os.path.isjunction` auslassen |
| Lauf blieb auf „dran“ hängen | Bricht eine Antwort an einem API-Fehler ab (z. B. Limit), sendet Claude Code `StopFailure` statt `Stop` | Der Hook beendet den Lauf jetzt, `update` trägt das Ereignis nach | Danach Claude Code einmal neu starten |
| Eigene Skripte lieferten unter Windows nichts (`stdout` ist `None`) | `subprocess.run(..., text=True)`: Umlaute in der Ausgabe lassen das Lesen still scheitern | Alle Aufrufe im Starter mit fester Kodierung, ein Test prüft das | Immer `encoding="utf-8", errors="replace"` |
| `git worktree remove` löschte Dateien ohne Rückfrage | Ignorierte Dateien zählen nicht als Änderung und werden mit entfernt | Vorher `git status --porcelain --ignored` ansehen | Was Wert hat zuerst sichern, nie `--force`, Liste und Ja des Besitzers |
| Zweite Anleitung bekam spätere Regeln nicht | `--ziel` merkte sich eine Datei nicht, wenn sie schon über `CODEX_HOME` dabei war | Seit Fassung 2026-11-07 gemerkt | Nichts tun, oder `--ziel` einmal neu aufrufen |
| Postfach meldet „Das Zertifikat stimmt nicht“, im Browser geht es (Windows) | Python kennt nur Stammzertifikate, die Windows schon geladen hat. Fehlende lädt Windows erst, wenn ein Windows-Programm sie braucht. So von einem Windows-11-Rechner gemeldet, hier nicht nachgestellt | Die Prüfung bleibt an | Einmal über Windows verbinden (PowerShell, .NET `SslStream` zum selben Server), dann noch einmal versuchen. Nie die Prüfung abschalten |
| `unrecognized arguments` bei einem Text mit „…“ (PowerShell) | PowerShell behandelt typografische Anführungszeichen wie normale und beendet die Zeichenkette | – | Längere Texte immer mit `--text-datei`, siehe `AGENTS.md` |
| `wunsch-notiz 7 --text "…"` suchte eine Datei mit dem Text als Namen | Der Client nahm `--text` als Kurzform von `--text-datei` | Seit Fassung 2026-11-08 keine Kurzformen mehr, `--text` geht auch bei `wunsch-notiz` und `bericht-antwort` | Nichts tun |
| Wunsch war plötzlich abgehakt, obwohl nicht fertig | Die Zentrale hakte ihn nach der letzten Aufgabe selbst ab | Seit Fassung 2026-11-08 bleibt er offen | Solche Wünsche mit `Alle Schritte erledigt` im Ergebnis ansehen und, wenn nötig, wieder öffnen |
| Antwort des Besitzers war für einen Chat nicht mehr neu | Ein anderer Chat desselben Agenten hatte den Bericht gelesen | Seit Fassung 2026-11-08 zählt Lesen nicht mehr als Abholen | Siehe `AGENTS.md`, Berichte |
| Mit `--heimnetz` antwortet die Zentrale auch im normalen WLAN (Windows) | Beim ersten Lauschen fragt Windows, ob Python ins Netz darf. Ein Klick auf „Zulassen“ legt Regeln „Python“ für jede Adresse an, die neben der eigenen Regel für Tailscale gelten. So von einem Windows-11-Rechner gemeldet | Die Zentrale weist alles außer Tailscale mit einer Fehlermeldung ab und gibt keine Daten heraus | Die breiten Regeln trotzdem abschalten, nur mit Ja des Besitzers: in PowerShell `Get-NetFirewallApplicationFilter -Program *python*` zeigt sie. Der Port soll nur für Tailscale offen sein |
| Jedes Update änderte `settings.json` von Claude Code (neue Reihenfolge, neue Kopie daneben) | Der Hook-Einrichter trug seine Einträge jedes Mal neu ein | Seit Fassung 2026-11-10 schreibt er nur, wenn ein Ereignis fehlt oder sein Skript nicht mehr da ist; `update --ohne-hooks` lässt den Schritt ganz aus | Alte Kopien `settings.json.vor-zentrale-*` dem Besitzer zeigen, löschen tut er selbst |

Neuer Stolperstein? Nicht hier eintragen (Änderungen in diesem Ordner blockieren das nächste Update), sondern als Notiz
`Anleitungen/Stolpersteine.md` (`notiz-ergaenzen`), und dem Besitzer sagen, damit er es an den weitergibt, der das Repo
pflegt. So hat der nächste Rechner das Problem nicht mehr.
